## 0. 结论先说

| 判断 | 结论 | 依据 |
|---|---|---|
| 代码能不能跑 | **能** | `mvn package` 一次通过；作业原始算子在全量 1 亿条数据上跑通，13,094 个窗口的 8 项指标与离线口径**逐窗口零差异** |

**一句话总结**：项目本身的代码和计算逻辑是可靠的，问题集中在「可复现性」——脚本、路径、数据准备步骤没有做到开箱即用；另外 README 里 12,960 个窗口的实测口径需要修正（实测为 13,094，与离线完全一致）。

### 2.5 作业算子全量跑通（1 亿条）

方式：把 Source 换成 CSV，Sink 换成文件，**中间的时间戳提取、Watermark、窗口、聚合、漏斗、TopN 全部复用作业原有内部类**（`MetricsWindowProcess`、`CountAggregate`、`CountWindowProcess`、`TopNProcess`、`FunnelSplitter`），并行度 1，本地 Flink 运行时。

| 指标 | 实测值 |
|---|---|
| 输入 | 100,150,807 行（排序后） |
| 保留 | 100,095,873 行（丢弃 54,934 脏时间戳） |
| 耗时 | **148 秒**（≈ 67.6 万条/s，单机、Source 并行度 1） |
| 输出窗口 | **13,094** 个，无重复行 |
| 指标对账 | 13,094 个窗口 × 8 项指标（pv/uv/cart/fav/buy/stage1/stage2/stage3）**差异 0 个** |
| 总量对账 | Σpv 89,661,330 / Σcart 5,530,446 / Σfav 2,888,258 / Σbuy 2,015,839，与全量离线统计**完全相同** |
| 漏斗总量 | stage1 67,237,704 / stage2 2,224,359 / stage3 163,905（用户级逐层交叉） |
| TopN | 1,296,638 行，覆盖全部 13,094 个窗口；134 个窗口商品数不足 100 条；单商品单窗口峰值 3,432 次 |

**对 README 的修正**：README 说「流式 12,960 个窗口，离线 13,094 个，相差 134 个，源于窗口边界对齐方式不同」——本次实测在**正确排序**的输入下，流式结果就是 **13,094**，与离线一字不差。原因是两边的边界算法本来就一样（`TumblingEventTimeWindows` 对齐 epoch 整分钟，等价于 `ts // 60 * 60`）。那 134 个缺口更可能是当时回放时**迟到数据被丢弃**造成的，属于数据丢失而非边界差异。建议 README 改写为「排序回放后流式与离线窗口数一致（13,094）」。

## 4. 运行操作步骤

### 4.1 方案 A：全容器（Linux / macOS / Windows+WSL2，推荐）

```bash
# 0) 前置
java -version && mvn -v && docker compose version

# 1) 构建作业 jar（仓库不含 target，必须自己打）
mvn -f flink-job/pom.xml clean package -DskipTests
# 产物：flink-job/target/realtime-analysis-1.0.jar（约 44 MB）

# 2) 拉起 Kafka / Flink / ClickHouse / Nginx
docker compose up -d
docker compose ps            # 等 kafka 变成 healthy

# 3) 建 topic（3 分区，与作业并行度对齐）
docker exec kafka kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic user_behavior --partitions 3 --replication-factor 1

# 4) 提交作业（容器内路径 /opt/flink/usrlib 挂的是宿主机 flink-job/target）
docker exec jobmanager flink run -c com.example.realtime.RealtimeAnalysisJob \
  /opt/flink/usrlib/realtime-analysis-1.0.jar \
  --kafka kafka:9092 --clickhouse "jdbc:clickhouse://clickhouse:8123/rt"

# 5) 准备数据（首次）：下载天池数据集 → data/UserBehavior.csv
#    关键：必须按事件时间排序，否则 96% 的记录会被当作迟到数据丢掉（见 5.2）
python -m pip install "kafka-python>=3.0"
python tools/sort_dataset.py --file data/UserBehavior.csv --out data/UserBehavior.sorted.csv

# 6) 回放（宿主机 → 容器 9094）
python producer/replay_producer.py --file data/UserBehavior.sorted.csv \
  --rate 0 --bootstrap localhost:9094 --topic user_behavior

# 7) 看结果
#    大屏：http://localhost:8090     Flink UI：http://localhost:8081
curl -s "http://localhost:8124/" --data-binary \
  "SELECT count() AS windows, sum(pv) AS pv, sum(uv) AS uv, sum(buy) AS buy, max(window_start) FROM rt.metrics_1min"
```

**预期结果（全量回放结束后）**：`windows=13094`、`pv=89661330`、`buy=2015839`（本次实测口径，可用于自检）。

## 5. 问题清单与修改建议

> 分级：**P0 = 不修就跑不起来 / 结果是错的；P1 = 能跑但不可信、不可运维；P2 = 性能与工程质量。**

### P0-1 仓库不含构建产物，快速开始必然失败

- 位置：`.gitignore`（`flink-job/target/`）+ `README.md`「快速开始」+ `start-all.cmd:17`、`pipeline_up.sh`、`anchor.sh`
- 现象：克隆后 `flink-job/target/` 不存在，脚本里 `flink run .../realtime-analysis-1.0.jar` 直接报 `FileNotFoundException`。
- 建议：
  1. README 第一步显式加 `mvn -f flink-job/pom.xml clean package -DskipTests`；
  2. 启动脚本增加守卫：
  ```bat
  if not exist "flink-job\target\realtime-analysis-1.0.jar" (
      echo [build] jar not found, building ...
      pushd flink-job && call mvn -B clean package -DskipTests && popd
  )
  ```
  3. 或提供 `Makefile`：`make build` / `make up` / `make replay` / `make verify`。

### P0-2 回放前必须按事件时间排序，否则丢 96% 数据（最严重）

- 位置：`README.md`「回放数据」、`producer/replay_producer.py`
- 现象（实测）：原始 CSV 的行序是**按用户/随机打散**的（同一分钟的记录散落在 3.5 GB 文件各处）。作业用 `forBoundedOutOfOrderness(5s)`，Watermark 会迅速推进到接近最大时间戳，之后到达的记录全部判为迟到丢弃。
  - 取前 30 万行（乱序）直接跑作业算子：输出 **5,898 个稀疏窗口**、PV 合计 **10,618**；而离线口径应为 **269,201**，**保留率仅 3.94%**。
  - 排序后跑全量 1 亿条：13,094 个窗口、Σpv 89,661,330，与离线**完全一致**。
- 建议：
  1. README 增加排序步骤（仓库自带的 `replay_tianchi.sh` 用的是 `~/userbehavior_sorted.csv`，说明作者自己排序过，但文档没写）；
     ```bash
     # 3.5 GB 建议 GNU sort（比 Python 快一个量级）
     LC_ALL=C sort -t, -k5,5n -S 4G --parallel=2 -o data/UserBehavior.sorted.csv data/UserBehavior.csv
     ```
     或直接用本次提供的 `tools/sort_dataset.py`（外部归并，纯 Python，4 分钟）。
  2. `replay_producer.py` 增加**单调性预检**：读取前 10 万行，若时间戳乱序比例 > 1% 就打印醒目告警并 `--force` 才能继续。
  3. 长期方案：作业侧 `allowedLateness` + 侧输出流（见 P1-1），但排序仍是回放场景的正确做法。

### P0-3 硬编码的主机 IP 与家目录路径

- 位置：`start-all.cmd:15,17`（`172.31.192.1:8124`）、`pipeline_up.sh`、`anchor.sh`、`replay_tianchi.sh`、`replay_final.sh`（`~/kafkaRT`、`~/flinkRT`、`~/userbehavior_*.csv`）
- 现象：WSL2 的宿主网关地址是**动态分配**的（本次机器上就与 172.31.192.1 不同），换机/重启 WSL 后 JDBC 连接直接失败；`~/flinkRT`、`~/kafkaRT` 也没有任何脚本负责创建。
- 建议：
  ```bash
  # 在 WSL 内动态获取 Windows 宿主 IP
  CH_HOST=$(ip route show default | awk '{print $3}')
  # 或者更稳的做法：ClickHouse 也放进 WSL/容器网络，用服务名互访
  ```
  把 `CH_HOST` 作为参数传给 `flink run`；把目录改成环境变量 `FLINK_HOME` / `KAFKA_HOME`，并提供 `scripts/setup-wsl.sh` 一次性安装。

### P0-4 脚本与文档自相矛盾

### P1-1 迟到数据被静默丢弃，且不可观测

- 位置：`UserBehaviorDeserializer:107-109`（catch 后什么也不做）、作业未配置侧输出
- 影响：丢了多少、为什么丢，线上完全看不见；本次验证就靠离线对账才发现「乱序会丢 96%」。
- 建议：
  ```java
  // 1) 反序列化/过滤处打点
  getRuntimeContext().getMetricGroup().counter("dirtyRecords").inc();

  // 2) 窗口侧迟到数据旁路
  OutputTag<UserBehavior> late = new OutputTag<UserBehavior>("late") {};
  SingleOutputStreamOperator<WindowResult> metrics = events
      .windowAll(TumblingEventTimeWindows.of(Duration.ofMinutes(1)))
      .allowedLateness(Duration.ofMinutes(1))
      .sideOutputLateData(late)
      .process(new MetricsWindowProcess());
  metrics.getSideOutput(late).addSink(deadLetterSink);   // 或再写一个 Kafka topic
  ```

### P1-2 ClickHouse 结果表无去重，重跑/重启会重复累计

- 位置：`db/init.sql`（三张表都是 `MergeTree`）+ `RealtimeAnalysisJob` 的 `JdbcSink`
- 影响：作业失败重启（`fixedDelayRestart` 会重放上一个 Checkpoint 之后的数据）、或手工重跑时，同一 `window_start` 会出现多行；大屏 `ORDER BY window_start DESC LIMIT 30` 会画出重复点，`sum()` 直接翻倍。
- 建议：
  ```sql
  -- 幂等写入：按 window_start 去重，保留最新版本
  CREATE TABLE rt.metrics_1min (
      window_start DateTime, window_end DateTime,
      pv UInt64, uv UInt64, cart UInt64, fav UInt64, buy UInt64,
      ver UInt32 DEFAULT toUnixTimestamp(now())
  ) ENGINE = ReplacingMergeTree(ver) ORDER BY window_start;
  ```
  查询侧用 `SELECT ... FROM rt.metrics_1min FINAL` 或 `GROUP BY window_start, argMax(...)`；`funnel_1min`、`item_topn_1min` 同理（ORDER BY 加 stage / item_id）。

### P1-3 消费位点用 `earliest()`，重启即全量重放

- 位置：`RealtimeAnalysisJob:115`
- 影响：作业重启/重新提交会从最早位点重读整个 topic，配合 P1-2 的无去重，结果直接污染。
- 建议：
  ```java
  .setStartingOffsets(OffsetsInitializer.committedOffsets(OffsetResetStrategy.EARLIEST))
  ```
  首次回放需要从头读时，用参数显式控制（`--from-earliest`），而不是写死。

### P1-4 时区可能导致大屏时间偏 8 小时

- 位置：`RealtimeAnalysisJob` 三处 `ps.setTimestamp(Timestamp.from(Instant.ofEpochMilli(...)))` + `db/init.sql` 的 `DateTime`
- 影响：`DateTime` 不带时区，ClickHouse 按**服务端时区**解析；JDBC 驱动又按 JVM 默认时区格式化。WSL/容器默认 UTC 时，存进去的 `window_start` 会比北京时间早 8 小时，大屏横轴整体偏移。
- 建议：建表改 `DateTime('Asia/Shanghai')`，并给容器设 `TZ=Asia/Shanghai`；或用 `ps.setObject(i, LocalDateTime.ofInstant(inst, ZoneId.of("Asia/Shanghai")))`。改完用 `SELECT window_start FROM rt.metrics_1min LIMIT 1` 和源数据首条时间对比确认。

### P1-5 Checkpoint 未外部化、状态后端在堆内存

- 位置：`RealtimeAnalysisJob:101` 只开了 checkpoint，没有 `setCheckpointStorage`、没有 `RETAIN_ON_CANCELLATION`
- 影响：集群重启/作业取消后状态丢失，无法从 Savepoint 恢复，也不能做不停机升级。
- 建议：
  ```java
  env.getCheckpointConfig().setCheckpointStorage("file:///opt/flink/checkpoints");
  env.getCheckpointConfig().setExternalizedCheckpointCleanup(
      ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION);
  env.setStateBackend(new EmbeddedRocksDBStateBackend(true));  // 状态放大后用
  ```

### P1-6 `bitnami/kafka:3.7` 镜像存在拉取风险

- 位置：`docker-compose.yml:5`
- 说明：Bitnami 自 2025 年起调整镜像目录，免费镜像迁移到 `bitnamilegacy/*`，`bitnami/kafka:3.7` 在新环境可能 404。另外 Kafka 3.7 已偏旧。
- 建议：换成官方 `apache/kafka:3.9.1`（或 `bitnamilegacy/kafka:3.7` 兜底），同时保留 `KAFKA_CFG_*` 到 `KAFKA_*` 的配置名调整（官方镜像用 `KAFKA_LISTENERS` 等）。

### P1-7 Python 依赖未锁定

- 位置：仓库无 `requirements.txt`；README 只写 `pip install kafka-python`
- 说明：本次用 kafka-python **3.0.11** 实测可用；老的 2.0.x 在 Kafka 4.x broker 上有协议协商失败的风险，不同人装出不同版本会得到不同结论。
- 建议：加 `requirements.txt`（`kafka-python>=3.0,<4`），并在 README 注明「Kafka 4.x 需 kafka-python ≥ 3」。

### P1-8 没有任何自动化测试

- 现状：仓库无 `src/test`，窗口口径、漏斗、TopN 全靠人工对账。
- 建议（性价比最高的三个测试）：
  1. `MetricsWindowProcess` 单测：构造 10 条固定数据，断言 pv/uv/漏斗数值；
  2. `UserBehaviorDeserializer` 单测：合法/非法行为、越界时间戳、坏 JSON 三种输入；
  3. Flink `MiniClusterWithClientResource` 端到端：`fromElements` → 窗口 → 断言输出条数。
  有了这三个，改口径时不用再跑一遍 1 亿条。

### P2-1 `windowAll` 单并行是吞吐上限

- 位置：`RealtimeAnalysisJob:146-149`
- 影响：指标支路并行度恒为 1，1 亿条本机 148 s（约 67 万条/s）看着够用，但数据量或窗口复杂度上来后一定是瓶颈，而且它是全局单点。
- 建议：两阶段聚合——`keyBy(随机桶号)` 局部聚合（计数 + 每桶 UV 集合）→ 再按窗口 `keyBy(windowStart)` 合并。桶数取 8~16，UV 合并时把桶内 HashSet 求并集（或各桶用 HLL 再 merge）。

### P2-2 UV 用 `HashSet` 精确去重

- 位置：`MetricsWindowProcess:258-260`
- 影响：单窗口 2.3 万用户没问题（约几百 KB），但窗口放大到小时级就会到 GB 级，且 Checkpoint 要序列化这些集合。
- 建议：`hyperloglog`（约 0.8% 误差、内存固定）或 RoaringBitmap（精确 + 压缩）。

### P2-3 TopN 的排序与定时器注册

- 位置：`TopNProcess:391-418`
- 影响：① 每来一条记录都 `registerEventTimeTimer`，同 key 同时间戳会被去重，但注册本身有开销；② `onTimer` 把所有商品取出来全量排序（O(n log n)），单窗口商品数千个时无感，商品数上百万时就慢了。
- 建议：用 `ValueState<Boolean>` 标记「本窗口已注册过定时器」；排序换成固定大小最小堆（只保留 Top100）。

### P2-4 结果类不满足 POJO，退化为 Kryo

- 位置：`RealtimeAnalysisJob:431-488`（`WindowResult` / `ItemCnt` / `TopNRow` / `FunnelRow` 只有 public 字段，无 getter/setter）
- 影响：序列化体积与 CPU 开销高于 POJO，跨版本兼容性差。功能上没问题，但这是个「面试官一看就知道你懂不懂 Flink 序列化」的细节。
- 建议：补齐无参构造 + getter/setter（保持 public 字段也行），让 Flink 走 `PojoSerializer`。

### P2-5 大屏工程的健壮性

- `dashboard/index.html:91,130` 每次刷新用 `(SELECT max(window_start) ...)` 子查询，数据量大时是全表扫描；建议前端缓存上次窗口或用 `ORDER BY ... LIMIT 1` 的物化视图。
- 只有「最新窗口」，没有时间范围选择/回放控件，演示时无法回看历史。
- `fetch` 无超时与重试退避，ClickHouse 慢查询时会叠加请求；建议加 `AbortController` 超时。
- `echarts.min.js` 直接放在仓库里（约 1 MB），可接受，但建议注明版本。

### P2-6 工程质量杂项

- 无 `LICENSE`（README 说「学习用途」，但没有许可证文件，别人不能合法复用）。
- 无 CI（GitHub Actions 跑 `mvn -B package` + 单元测试即可）。
- 根目录散落 `*.log`、`*.err`、`retry_pulls.*`、`.backup-path-fix-20260919/` 等临时产物（部分已被 .gitignore 覆盖但本地仍在），建议清理。
- `runtime/` 里放了 600 MB 的 Flink/Kafka 发行包（已 gitignore），新机器仍需自行下载，README 没写下载地址与版本。
